---
title: Follow returns and refunds
description: See which returns need you, follow each one from request to refund, work it in a return case and tell a requested refund from money returned.
---

Returns shows every return a connected store shares with Luma, and every refund that no return settles. Each return keeps its order, items, reasons, refunds and the evidence Luma read. Luma reads your store’s returns and refunds. A return case can also request creation or approval of a Shopify return. Receipt and refunds stay separate steps, and Luma reads the store’s results on its next sync. To record what arrived, how it was judged and how to settle it, work the return in a [return case](#work-a-return-in-a-case). Open **Returns** in the sidebar or press **G**, then **T**.

## Find returns that need you

The cards at the top count returns in each open stage. Select a card to list those returns:

- **To review**: a customer asked to return items. Approve or decline the request in your store.
- **Waiting for items**: the return is approved and not every unit has arrived back.
- **Ready to refund**: the items are back, or weren’t expected back, and haven’t been refunded.
- **Refund processing**: a refund payment is still with the payment provider. The customer hasn’t received the money yet.
- **Refund failed**: every payment attempt for the refund failed. Retry the refund in your store.
- **Ready to close**: the items are back and refunded, but the return is still open.

The views group the stages. **Needs action** lists requests to review, returns ready to refund or close, and failed refunds. **Waiting** lists returns waiting for the customer’s items or for a refund payment to finish. **Done** lists closed, declined and canceled returns and completed refunds. **All** lists everything.

Choosing a card narrows the list to that stage while the other cards keep their counts. A card for a stage outside the current view, such as **Refund processing** in **Needs action**, switches to **All**. The tabs above the list also include the views you and your team saved, and opening **Returns** from the sidebar returns to the view you used last.

Search by return name, order number, return reason or the return, refund or order ID in your store. When you can view customers and the store shares contact details, search also finds returns by the customer’s name or email address. **Stage**, **Refund state** and **Source** above the list narrow it in one click. For anything else, choose **Filter** and pick a field, such as **Kind**, **Reasons**, **Items**, **Refund processing**, **Value of returned items**, **Failed payment attempts**, **Partly received**, **Requested** or **Last activity**, then a condition and a value. Amounts compare only within one currency, and **Partly received** is unknown when the store doesn’t report which items arrived. The sort menu after **Display** names the current order; **Needs action** and **Waiting** start with the oldest request, the other views with the newest. Choose the sort menu to sort by stage, request date, last activity, value or the amount still processing, or to flip the direction. **Clear** removes every filter and the search.

Search can match customer names, so your search text stays on the page: it isn’t saved in the page address or in views, and it’s cleared when you leave or reload the page. A link that opens Returns with a search, for example from another page, fills in the search and then removes it from the address. Filters, sorting and display are saved.

## Arrange the list

Choose **Display** to change how the list looks:

- **Layout**: **Table** shows columns, **List** shows one row per return with the properties you choose, and **Board** shows a column per group.
- **Columns** or **Properties**: choose what each return shows and drag them into order. In the table you can also resize, move, pin and hide columns from each column’s menu.
- **Group by**: group returns by stage, refund state, kind, reason or source, and by request date by day, week or month. Stages follow the order a return moves through them. Each group shows how many returns it has and the value per currency. A return with several reasons appears in each reason’s group. **Incomplete** means a store is still importing returns.
- **Density**: **Compact** fits more returns on screen.
- **Open records in a preview**: choosing a return shows its stage, next step, money, dates, order and items beside the list instead of opening it. From the preview you can narrow the list to its stage, refund state, source or a reason, or hide it. **Open full return** opens the return.

Grouped by stage, the board shows a column per stage. You can’t move returns between columns, because their stage comes from your store.

## Save and share views

When you change filters, sorting, grouping or display, the view is marked **Modified**. Choose **Save** to update a saved view you can edit, **Save as new view** to keep your changes as a new view, or **Reset** to return to the view as it was saved. Sharing a view never gives anyone access to returns they can't see; see [Saved views](/docs/saved-views). Copy a view’s link or pin it to the sidebar from **View options**. When you open a return, **Returns** in the bar at the top returns to the list with your view.

## Work from the keyboard

- **J** and **K**, or the arrow keys, move through the returns. On a board, the arrow keys also move between columns.
- **Enter** opens the return you're on.
- **Space** opens or closes it in the preview, when the preview is on.
- **X** selects a return, **Shift**+**X** selects a range, and **Esc** clears the selection or closes the preview.
- **/** goes to search, **F** adds a filter and **?** lists these shortcuts.

## Money returned

A refund counts as money returned only when its payment succeeded. A return shows three amounts separately:

- **Refunded to the customer** adds up successful refund payments.
- **Processing** adds up refund payments that haven’t finished. The customer hasn’t received this money yet.
- **Value of returned items** is what the returned units were worth after discounts. It isn’t an amount refunded.

A refund recorded without a payment, for example a restock without money back, shows as **Recorded without payment**, and no money was returned through it. Failed payment attempts stay listed, even after a later attempt succeeded. Amounts in different currencies are never added together; each payment is listed under **Refunds** instead.

## Read a return

A return shows its next step and its progress from request to close, with the time each step happened in your store:

- **Items** lists each returned item with its reason, and the units received, restocked and refunded. Open an item to see its product and stock.
- **Refunds** lists each refund with every payment attempt and the units it covered.
- **Money** shows the amounts above.
- **Order** shows the order the return belongs to, with its status, payment and total.
- **Source and evidence** shows the store, the return’s ID, when Luma last read it and when it last synced returns.
- **Source history** lists each state Luma read, newest first. It shows the state at that moment, not every change in between.
- **Other returns of this order**, when there are any.

For Shopify orders, **Order details from Shopify** shows the customer, payments and events, read live with your connection’s permissions. You can also open a return from **Returns and refunds** on an order.

## Wait for items to arrive back

While a return is **Waiting for items**, its next step says how many units are still on their way and how many have arrived, for example “Waiting for 2 units to arrive back. 1 of 3 received.” Luma moves the return to **Ready to refund** once your store reports every unit received.

If the store doesn’t report received items, the step says so rather than assuming the items arrived. Check the return in your store before you refund it.

## Work a return in a case

A return case is Luma’s own record of a return: the units the customer sends back, what arrived, how each unit was judged and how you propose to settle it. Your store’s record of the return stays as it is.

- To work a store return, open it and select **Work this return in a case**. Its lines are prefilled.
- To start without a store return, open the order and select **Open return case** beside the **Returns and refunds** title. Choose the lines, the units and a reason for each. If the order comes from more than one system, choose the source the items belong to.

Each unit counts once. Units already in another case, or in a store return that no case works, can’t be added again, so partial returns of one order never add up to more than was ordered.

Work the case in three steps:

1. **Record receipt**: enter the units that arrived back for each line. Units that didn’t arrive count as missing.
2. **Record inspection**: judge every received unit as resellable or damaged.
3. **Propose resolution**: choose a refund, exchange, store credit or rejection, and how many resellable units go back to stock. Damaged and missing units can’t be restocked, and a rejection restocks nothing.

A proposal doesn’t refund, restock or exchange anything. Add a note, or a link to a photo or document, as evidence with each step. Recording an earlier step again replaces it and clears the steps after it. **History** keeps every decision with who made it and when.

Under **Receives and inspects**, assign the person who handles the parcel. Only people who can manage returns can be assigned. **Cancel case** keeps the case in the history and makes its units returnable again.

## Create the return in JTL-Wawi

For an order from JTL-Wawi, a case can create the return in JTL-Wawi, so your warehouse can receive it there:

1. On the case, select **Create return in**, followed by your connection’s name. Choose the warehouse that receives the items and the return reason, then select **Request approval**.
2. Someone else approves the request on the case. They need **Manage returns**, **Approve or reject changes** and **Create returns in JTL**. Luma then creates the return once.
3. Luma reads JTL-Wawi again and shows the return number once it finds exactly the approved return.

Luma creates the return without a credit; a refund stays a separate decision in JTL-Wawi. A request expires after 24 hours. If Luma can’t send an approved request right away, it sends it later while the approval is still valid; a request that wasn’t sent in time shows **Expired**, and you request it again. If JTL-Wawi doesn’t confirm the request, the case shows **Not confirmed**: select **Check**, followed by your connection’s name, to read it again. Luma never sends the request a second time. In an observe-only workspace, Luma records the request and sends nothing.

The JTL-Wawi connection needs access to returns. A connection set up before returns were available must be reconnected; see [Apps and connections](/docs/apps-and-connections#change-or-reconnect-a-connection). Shopify can also create returns when the connection has return write access. A case linked to a customer’s requested return asks for approval of that exact request; an unlinked case creates a new return. Luma checks the lines and quantities before sending and reads Shopify independently to verify the result. Missing or uncertain results stay **Not confirmed**, and Luma never sends them again. This action does not refund or restock items. Cin7 Core cannot create returns from Luma.

## When returns are missing

Returns appear only from connections that share them:

- **No connection shares returns yet** means none of your connected stores shares returns and refunds with Luma.
- A Shopify store connected before Luma could read returns must be reconnected to share returns and refunds. The Returns page names each store that needs it. Someone with **Manage connections** can reconnect it; see [Apps and connections](/docs/apps-and-connections#change-or-reconnect-a-connection).
- JTL-Wawi doesn’t share returns with Luma. Returns handled only in JTL-Wawi don’t appear here; a return Luma created in JTL-Wawi shows its number on the return case.
- Shopify shares returns for orders from the last 60 days unless access to older orders is on for the store.

Luma checks for new and changed returns regularly and reads every return again once a day. [Data sync](/docs/data-sync) shows the progress for each store.

Viewing returns and return cases needs **View returns**. Without it, Returns is hidden from the sidebar and search. Opening and working return cases needs **Manage returns**.

## Review a return with a customer

Open the return case from its order, customer, workspace search or **Needs you**. The service
timeline shows store events alongside receipt, inspection and other case decisions. Each event
names its source; store evidence includes when Luma read it.

Use **What you can tell the customer** to explain what is known. Pending payments are still processing. Failed
attempts did not confirm a payment. Old or unavailable evidence needs another read before you
confirm money returned. A recorded resolution proposal has not changed the connected systems.

Check the next step, owner and waiting reason before handing the case over. If no deadline has
been configured, the view says so. Assign the case to a person who can manage returns.

## Settle the case

After recording receipt, inspection and a refund proposal, use **Stock and refund** on the case.
Request the refund separately from restocking resale units. Choose the mapped Wawi item and actual
warehouse for each restock. Damaged and missing units cannot be restocked; missing units cannot be
refunded through this case action.

Someone else approves each request with the relevant app permission. Luma sends the approved action
once and reads the system again. If it can’t send right away, it sends later while the approval is
valid; an action not sent within 24 hours shows **Expired** and needs a new request. **Refund processing** means the money is still processing. **Failed**
means the payment did not succeed. Use **Check source** when a response or payment is uncertain.
Checking never issues a second refund or stock addition.

A successful refund does not prove stock changed, and a successful restock does not prove the refund
was paid. Review both results and their read times. An old check needs a new read before you confirm
the result to the customer. Once an action was sent, receipt, inspection and the proposal stay fixed;
you can still hand the case to another owner. Wawi stock settlement is available in the simulator;
your live connection must support the action before it can be used.

To see what a creation, refund, restock or exchange step relied on, open **Evidence** on it. It shows the reads and the system’s write receipt, when Luma read them and whether the reads were complete. See [Read the evidence](/docs/issues/resolve#read-the-evidence).

## Coordinate an exchange

Record receipt and inspection, then propose **Exchange**. In **Exchange**, choose a replacement
that is explicitly mapped to Shopify and Wawi and enter its quantity. Request replacement approval.
Someone else approves the exact request. Reported available stock is not a reservation.

After the request is independently verified, request processing approval. Luma checks availability
again and uses Shopify's current financial quote. The replacement fulfillment and the price difference
have separate progress. A requested charge is pending until successful payment is independently read.
Use **Check source** after payment, then request payment hold release approval. Other holds remain.
An exchange refund difference is also pending until its payment succeeds.

If stock becomes unavailable, the case owner chooses **Wait for this item**, **Choose a different item**
or **Choose a refund**. Luma never chooses automatically. A different item or refund needs cancellation
approval and fresh cancellation proof first. After cancellation, choose the different replacement or
continue to the separately approved refund settlement. This preserves the approved resale stock units.
A processed exchange needs an owned handoff instead of another replacement request.

Arrange and verify the Wawi replacement allocation before shipping. The Shopify replacement request
does not prove an ERP reservation. Settle returned stock separately and review both systems before
confirming that the case is complete.

## Set return deadlines

Open **Return deadlines** on Returns. Choose the hours allowed for receipt, inspection and a
resolution proposal, and financial follow-through. Select **Configured**, then **Save deadlines**.
Enable **Follow up on overdue return steps** in Workflows to monitor automatically.

Receipt is due from case opening. Inspection is due from the recorded receipt, and the proposal
from inspection. Financial work is due from the proposal or its actual action request. Luma does
not invent a date for an event your store has not reported.

On the case, **Waiting and deadlines** shows the owner, due dates and earlier occurrences.
Select **Check progress** to reread evidence without changing either system. Missing units,
inspection, pending money, failed money and unavailable or stale evidence stay separate.
Only fresh financial evidence ends a payment wait. Repeated checks retain the same waiting
occurrence; a later recurrence keeps its earlier history. Reassign the case when another person
should own the next step.

### Complete an exchange

When adding the Wawi connection, select **Read exchange replacement orders and reservations** and
validate its access. An older connection without this access must be reconnected; see
[Apps and connections](/docs/apps-and-connections#change-or-reconnect-a-connection).

In the exchange case, open **Completion across both systems**. Record the actual warehouse receipt
in Shopify. Create one paid replacement order in Wawi using the **Replacement order reference**
shown in the case, the mapped replacement item and its exact quantity. Reserve those units for that
order. After Shopify processing, **Check both systems** shows the actual replacement total to use in
Wawi. It also identifies any stock, price, payment or reservation step that still needs attention.

Approve resale restocking separately. Wait for the actual price-difference payment or refund to
settle, and approve any payment hold release separately. Then check both systems again. Luma completes
the case only when its recorded units, source receipt, physical resale stock, one replacement order,
reservation and settled money agree. Pending money and an accepted action do not complete it.

An unresolved check stays with the case owner in Needs you. Review duplicate Wawi references and
connection access before retrying. Damaged units need a confirmed physical disposal; this system pair
cannot prove that disposal yet, so those cases remain owned and open. New stock movements may need
review before the final check can confirm the warehouse total.

You can check a completed exchange again. If fresh source evidence no longer agrees, Luma reopens the
case and keeps the earlier completion in its history.
