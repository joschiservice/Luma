# ADR-002: Canonical commerce data model v0

Status: accepted for the initial model. Decision: 2026-09-17, LUMA-5.

## Context and decision

The Exception Desk must compare JTL-Wawi and Shopify state, diagnose failures and trace a proposed fix through policy, execution and verification. Use small canonical aggregates with explicit source identities and immutable observations. Keep provider payloads in connectors, outside canonical rows. This document specifies the persistence contract for later Drizzle migrations; it does not install Drizzle or implement adapters.

Provider-shaped tables would leak connector semantics into rules. A universal ERP schema would expand scope without supporting more V0 cases. One mutable row with a `provider` field would lose disagreements between systems. Choose canonical identities plus source-specific snapshots and explicit authority for the current projection.

Ownership and imports follow [ADR-001](001-module-boundaries.md). Table references do not grant permission to import another module's schema or write its rows.

## Storage conventions

- SQL names use snake_case. Every table has an application-generated UUID `id` primary key. Every tenant-owned table also has required `tenant_id uuid` and `UNIQUE (tenant_id, id)`. The identity-owned organization root is the exception: its `id` is the tenant ID and it has no redundant `tenant_id`; do not create a second Tenant entity. Auth organization IDs must map one-to-one through identity if their representation differs.
- Mutable rows have `created_at`, `updated_at` (UTC `timestamptz`, required), and `version integer` (default 1, positive). Updates compare the expected version and increment atomically. Immutable rows have `created_at` only unless stated otherwise. These fields are implicit below; `?` means nullable, everything else is required with no implicit default.
- Use `uuid`, `text`, `integer`, `boolean`, `jsonb`, `numeric(20,6)` for quantities/money, and `timestamptz` for instants. Represent decimals as strings at application/transport boundaries; reject unsupported precision instead of rounding silently. Money is nullable and paired with a three-letter currency; never compare currencies without conversion. Quantities carry a unit and are comparable only in the same unit.
- Statuses are `text` with database `CHECK` constraints for the values listed below. JSON is limited to versioned, runtime-validated evidence, parameters and snapshots; indexed business identifiers, quantities and lifecycle fields are columns. Unknown source status maps to `unknown`, never to success or zero.
- Same-owner relationships use composite `(tenant_id, reference_id)` foreign keys to `(tenant_id, id)`, with `ON DELETE RESTRICT`. Add parent-qualified unique keys/FKs when a child must belong to the same order. Cross-owner references are logical UUIDs, checked through owner interfaces using tenant context; workflow steps tolerate missing projections and retry. Snapshot provenance is a narrow exception: orders and inventory snapshots use a composite `(tenant_id, connection_id, observation_id)` foreign key to immutable connector observations, with `ON DELETE RESTRICT`. This guarantees durable provenance without cross-owner queries or writes. No cross-owner Drizzle schema imports or cascade deletes.
- Every repository query includes tenant scope from authenticated context. [ADR-003](003-tenant-isolation-and-data-residency.md) additionally requires forced PostgreSQL RLS, transaction-local tenant settings and restricted runtime roles; identity bootstrap uses separately scoped access. Reject foreign-tenant references, including IDs in JSON, before persistence. IDs alone are not authorization. Tenant deletion is an explicit coordinated retention process, not a cascade.
- Index each FK and logical-reference lookup beginning with `tenant_id`. Add the unique and query indexes below. Never globally deduplicate provider identifiers, SKUs or incident fingerprints.

Drizzle implementation should express physical keys/checks/indexes in migrations and validate JSON at ingress. Type annotations alone are insufficient. See the official [PostgreSQL column mapping](https://orm.drizzle.team/docs/column-types/pg) and [constraint/index APIs](https://orm.drizzle.team/docs/indexes-constraints).

Fulfilled totals are calculated for a selected source and exclude cancelled/failed operations; overfulfillment is detectable evidence, not silently clamped data. Order status and payment status remain independent of fulfillment progress.

### Source snapshots and authority

Orders and inventory each own `entity_snapshots` and `projection_sources` tables within their own SQL namespace; these are not shared tables exposed through platform.

- Immutable `entity_snapshots`: `entity_kind text`, `entity_id uuid`, `connection_id uuid`, `observation_id uuid`, `normalizer_version text`, `snapshot jsonb`, `source_revision text?`, `source_updated_at timestamptz?`, `observed_at timestamptz`, plus tenant/ID/created time. Unique `(tenant_id, entity_kind, entity_id, observation_id, normalizer_version)`. Snapshot has a versioned owner-defined canonical schema, including explicit known/unknown fields. Index `(tenant_id, entity_kind, entity_id, connection_id, observed_at)`.
- Mutable `projection_sources`: `entity_kind text`, `entity_id uuid`, `field_group text`, `snapshot_id uuid`, `authority_policy_version text`. Unique `(tenant_id, entity_kind, entity_id, field_group)`. Snapshot is a same-owner FK; owner validates matching entity. Field groups initially identity, lifecycle, payment, quantities and tracking as applicable. These rows identify exactly which snapshot supplied the current fields.
- Workflows owns immutable `source_authority_versions`: tenant/ID/created time plus `policy_version text` and `required_field_groups jsonb` (a versioned manifest of required entity-kind/field-group pairs). Unique `(tenant_id, policy_version)`. `source_authority_rules` has tenant/ID/created time plus `policy_version text`, `entity_kind text`, `field_group text`, `connection_id uuid`; unique `(tenant_id, policy_version, entity_kind, field_group)` and FK `(tenant_id, policy_version)` to the version. Rules have no individual activation time.
- Workflows owns mutable `source_authority_activation`: common mutable columns plus `policy_version text?`, `activated_at timestamptz?`; unique `(tenant_id)` and FK `(tenant_id, policy_version)` to the version. Version/time are both null before initial activation or both set. This singleton per tenant is the only source of active authority; readers never select the latest rule or version by timestamp.
- Publication is one workflows transaction: ensure the tenant activation row exists using `INSERT ... ON CONFLICT (tenant_id) DO NOTHING`, lock it with `SELECT ... FOR UPDATE`, insert the version and its complete rule set, validate exact coverage of the manifest against the supported projection field groups and tenant configuration, then update the activation pointer/time and append the audit/outbox event. Commit all together or roll back all. Serialize concurrent publishers with the row lock and reject a stale expected activation version. Published manifests/rules cannot be extended, changed or deleted; every change publishes a new version through this path. Restrict writes to this publication use case. Readers capture the pointer once per evaluation and load all groups by that version; immutable historical versions remain available to in-flight work. Before an effect, recheck that the captured version is still active; otherwise reevaluate.
- Do not hardcode “JTL always wins.” Bootstrap requires a complete active version before projection or automation. Missing authority fails closed rather than falling back to another version. Other source snapshots remain available for mismatch rules. Inventory positions already separate connections; authority decides the intended correction direction, not which observation to discard.
- Commit projection, snapshot selection and owner outbox atomically. Workflows passes normalized observations through public ingest commands. Core rules consume typed snapshots, not raw JSON or provider branches.

The required `exceptions.state` constraint is:

```sql
CHECK (state IN (
  'detected', 'diagnosed', 'proposed', 'awaiting_approval', 'allowed',
  'executing', 'verifying', 'resolved', 'escalated', 'failed'
))
```

Normal transitions: detected → diagnosed → proposed → allowed → executing → verifying → resolved; when approval is required, proposed → awaiting_approval → allowed. `failed` and `escalated` are persisted states, not merely transition outcomes. Any unresolved state can transition to either; failed/escalated cases can return to diagnosed after new evidence and an audited transition. Only resolved is terminal; all other states remain active for fingerprint deduplication (`WHERE state <> 'resolved'`). A detection while active increments count/last time and appends evidence; duplicate evidence keys do not increment. A recurrence after resolution creates a new exception linked through `previous_exception_id`. Resolution requires passed verification, or an explicit human disposition such as false_positive/manual_resolution with actor, reason and evidence; the latter is not an autonomous verified success.

Fingerprint is a versioned hash of class, rule identity, stable subject and relevant source/location scope, excluding changing quantities/timestamps/error text. Use an atomic upsert and evidence dedupe in one exceptions transaction. Changing rule implementations should not fragment incidents unless the fingerprint definition changes intentionally.

Policy decisions/approval grants remain in policies (LUMA-10). Every attempt references an immutable decision binding tenant, actor, capability, action hash, policy version and outcome; grants also bind action hash and expiry. Recheck permissions, approval, preconditions and connection state before each effect. Withheld/denied authorization leaves auditable evidence and starts no running attempt. Proposal edits, expiry or stale evidence require reevaluation.

Execution idempotency key is `v0:<proposal UUID>` within the tenant. Retries reuse it and create new attempt numbers, never a new action. A caller reusing the key with different intent is rejected. Provider idempotency support is capability metadata; after a timeout with an uncertain effect, mark unknown and reconcile with a fresh read before retrying. Lack of safe reconciliation escalates. Verification records actual observations, checked postcondition, evaluator version and result independently from “request accepted.” Compensation is a new policy-checked proposal/action linked to the prior action.

## Audit and workflow references

`audit_entries` is owned by audit and append-only: common immutable columns plus `event_key text`, `event_type text`, `schema_version integer`, `occurred_at timestamptz`, `actor jsonb`, `subject_kind text`, `subject_id uuid`, `correlation_id uuid`, `causation_id uuid?`, `connection_id uuid?`, `proposal_id uuid?`, `executed_action_id uuid?`, `attempt_id uuid?`, `policy_decision_id uuid?`, `evidence_refs jsonb`, `details jsonb`. Unique `(tenant_id, event_key)` deduplicates producer events; index `(tenant_id, subject_kind, subject_id, occurred_at)` and `(tenant_id, correlation_id, occurred_at)`.

Actor schema: kind user, service, agent or connector; stable `id`; optional initiating user, model/provider/version, prompt version and run ID for agent actions. Executor provenance records the actual mechanism/adapter/model, distinct from the proposer and approver. Never store credentials, chain-of-thought or full customer payloads in audit details. Corrections append a new entry referencing the prior entry. The application audit role cannot update/delete entries; retention uses a separate controlled process. Append-only does not claim cryptographic tamper-proofing.

Workflow failure subjects need only an opaque workflow run UUID, worker/step key, attempt number, normalized error code and event time in evidence. Durable runtime execution records remain workflows-owned; their runtime-specific schema is deferred to the Restate/Temporal ADR. Connector failures use the connection UUID even when no commerce object exists.

Each owner persists its state change and audit/outbox event atomically. Audit ingestion deduplicates committed event IDs; no distributed database transaction is implied. Before an external effect, persist the prepared attempt and its policy/intent audit event durably. Recovery must reconcile prepared/running/unknown attempts. Record effect and verification evidence before advancing the exception outcome.

## Ingestion, provenance and retention rules

1. Derive tenant/connection from trusted connector context. Persist a source observation before projecting. Webhook dedupe uses connection + resource + provider event ID; polling uses a persisted run/page/item key reused on retries. A new poll receives a new run ID, even with unchanged values, to demonstrate freshness. Payload hashes alone are not event IDs.
2. Resolve external objects explicitly. Never join tenants or auto-merge on labels. An unknown relationship remains pending/unmapped; deterministic rules must expose the missing mapping rather than invent data.
3. Adapter normalization records API/adapter/schema version and source status semantics. Keep unknown/null distinct from explicit deletion and zero. Preserve provider revisions as opaque text. Order revisions only if the adapter declares a comparator; otherwise use trustworthy source update times. When either snapshot lacks a source update time, a later point-in-time read is the authoritative reread: the later observation time wins, and equal times between untimed snapshots fall back to the greater observation ID. Source update times and observation times are never compared with each other. Receipt time is not source order. Ambiguous/out-of-order observations remain evidence and require an authoritative reread before overwriting current state.
4. Omitted fields in a partial event do not erase values; explicit null has schema-defined meaning. Only a complete, successful collection or explicit tombstone can mark a missing item deleted. Failed/incomplete pagination never implies deletion. Tombstones preserve mappings/history and block stale resurrection under the same ordering rule.
5. Evaluate mismatch only with equivalent SKU/location/unit mappings and sufficiently fresh observations under a versioned rule freshness window. Record both observations, source times, threshold and rule version. Stale or incomparable values yield uncertainty/escalation, not stock writes.
6. Raw capture is optional and purpose-limited. Remove credentials before persistence, encrypt retained bytes, and authorize access by tenant. Require an explicit expiry at capture; deployment retention policy supplies duration. Keep minimum canonical personal data: canonical records hold no customer/address entity. Imported customer profiles (LUMA-96) live outside the immutable evidence stores in the customers module, keep only the current source version and are erased on redaction; contact and address fields are imported only under their own provider approvals. Purge raw bytes on expiry while leaving observation IDs, normalized evidence and purge metadata. Sensitive normalized fields follow the tenant's retention policy as well.
7. Versions answer different questions. The adapter version (`jtl/1`, `shopify/1`) identifies the normalization that produced an observation; bump it whenever the same provider response would produce different observation data, including a new optional field. A snapshot kind's `schemaVersion` identifies its document shape; bump it when fields are added, removed or change meaning, and keep readers and validation for every stored version. The normalizer version is part of snapshot identity; bump it whenever an existing observation would normalize to a different canonical document, so replay adds a snapshot rather than conflicting. Order snapshots are version 2 (`dueAt`, `placedAt`, `total`, line `skuCode`/`title`); stored version 1 order snapshots remain valid.

This documentation change is checked for repository formatting and consistency; database and provider tests belong to their implementations.

## Consequences and follow-ups

This model supports cross-system comparison without losing source disagreement. It adds explicit mapping, snapshots and workflow coordination; JSON snapshot schemas require versioned readers. Changing canonical identity or authority later requires audited remapping/reprojection, while additive nullable fields are inexpensive. Do not retain raw payloads forever merely to simplify reprocessing.

Returns and refunds were added later as order children with payment outcomes (LUMA-103, [Returns workspace](../returns-workspace.md)); they are observations, not a payment ledger.

Out of scope: full ERP accounting, tax, invoices, purchasing, customer master data, stock ledger/reservation management, bundles/BOMs and warehouse topology. Payment summary and stock totals are observations, not ledgers. LUMA-10 implements policy/audit enforcement; LUMA-16 defines capabilities; LUMA-17/18 validate provider mappings; LUMA-19 implements detection using golden fixtures. Hosting, retention durations and durable runtime choices remain their own decisions.
