# Observability

Luma's server processes can export errors, traces, model observations, product events and flags to hosted providers (Sentry, Langfuse and PostHog), or traces, metrics, logs and profiles to a local Grafana stack for diagnostics. Every exporter is optional and off unless configured. All telemetry follows one data policy: opaque correlation IDs and fixed operation names, never customer content, credentials or raw tenant identifiers. The browser loads no vendor SDKs, cookies, session replay or autocapture; it only sends an action ID through the typed API client.

## Hosted providers

Credentials go in the API and worker `.env` files; see `apps/api/.env.example`. Use separate projects and tenant hash secrets for development, staging and production.

- Only EU ingestion hosts are accepted: Sentry `o<org>.ingest.de.sentry.io`, `https://cloud.langfuse.com` and `https://eu.i.posthog.com`. There is no cross-region fallback. Operators must also verify each project's processing location, access and retention under [ADR-003](architecture/003-tenant-isolation-and-data-residency.md), and set retention before enabling customer traffic.
- `OBSERVABILITY_TENANT_HASH_KEY`, a random secret of at least 32 characters, is required whenever any exporter is enabled.
- Both Langfuse keys are required together; a partial pair fails startup.
- `OBSERVABILITY_SAMPLE_RATE` samples traces; all spans of a trace share the decision. Errors and explicit product events are not sampled.

The runtime initializes identity and telemetry before accepting requests. Closing the server flushes spans, shuts down processors, then drains analytics and Sentry. Network timeouts are bounded. A failed flag evaluation returns the caller's fallback (false by default), and analytics failures never fail a request. Flags never replace authorization checks.

## Correlation and tenant context

| ID                 | Source                                                                                             |
| ------------------ | -------------------------------------------------------------------------------------------------- |
| `x-luma-action-id` | UUIDv4 from the web client, reused across related calls and retries. Invalid values are discarded. |
| `x-request-id`     | Generated by the server for each HTTP request. Incoming request IDs are ignored.                   |
| `x-trace-id`       | The OpenTelemetry trace ID, shared by Sentry and Langfuse. PostHog events carry all three IDs.     |

`@luma/platform` exposes a framework-independent `Observability` interface. Composition roots inject it into application services; vendor SDK imports stay in the platform infrastructure adapter. Pass the immutable `TraceContext` explicitly through workflow, agent, model and tool operations; concurrent requests never share an ambient tenant context.

The API binds telemetry to `request.tenantContext` only after the identity guard succeeds, and handlers pass `request.observation.context` to application services. Background work calls `forTenant(context, authorizedTenantId, 'EU')` after reauthorizing. Exports carry an environment-specific HMAC as `tenant_ref`, never raw organization or user IDs; the pseudonym is still restricted metadata. Never derive tenant context from a header, body or analytics ID. Trace context grants no authority: reauthorize any persisted workflow envelope before resuming it.

Span names, product event names, flag keys and model names are explicit allowlists. Extend them in code review; never use customer content as a name. Tenant flag evaluation uses `tenant_ref`; anonymous evaluation uses the action or request ID.

## Data policy

General telemetry contains deployment metadata, correlation IDs, tenant HMACs, fixed operation names, status, timing, approved model names, token counts, model latency and reported cost. [Error reports](#error-reports) add diagnostic fields. There is no general-purpose metadata bag.

Never add emails, names, addresses, commerce identifiers, prompts, completions, tool arguments or results, URLs, query strings, request bodies, headers, cookies or credentials. The [model gateway](model-gateway.md) records model identity, token counts, latency and cost, never arguments or return values.

- Sentry default integrations and hosted automatic instrumentation are off; only linked errors and process-level error capture are on.
- Langfuse exports only Luma's tracer and masks input, output and metadata as a second boundary. Media upload is off.
- PostHog has GeoIP, exception autocapture, automatic flag events and person profiles off.
- Application HTTP logs contain request IDs, trace IDs, status and, for failed requests, error details. Default request logging is off.

Enabling framework or model auto-instrumentation requires export-level redaction tests first.

## Error reports

Unexpected failures are reported with their error type, message, stack, code and up to five linked causes:

- API requests that end with an internal server error, and failed readiness checks. Validation, payload-size and media-type errors and deliberate API errors such as `NOT_FOUND` or `SERVICE_UNAVAILABLE` are responses, not reports.
- Temporal activity failures, described below.
- Commerce sync worker failures: sync passes, supplier follow-up and scheduled detection. The fixed log message, such as `Sync pass failed; retrying.`, names the operation.
- Uncaught exceptions and unhandled promise rejections when Sentry is configured. The process still exits as Node would.

Sentry events contain the exception, the correlation tags `request_id`, `action_id`, `trace_id` and `tenant_ref`, and, for requests, the route pattern and method as tags and a redacted request with method, URL and headers:

- **URLs:** route words and UUIDs stay. Other path values become their route parameter name, such as `:skuId`, or `[Filtered]` when no route matched. Query values are `[Filtered]` except bounded view parameters such as `window`, `limit`, `sort` and `status`. Search text, cursors and OAuth codes and state stay filtered.
- **Headers:** cookies, authorization, tokens, secrets, sessions, signatures and HMACs, API keys, CSRF tokens, AWS signing headers, Shopify shop domains and client IP addresses are `[Filtered]`. The referrer is redacted like a request URL.

Request bodies, users, breadcrumbs, extras and custom error properties, such as PostgreSQL's `detail`, are never added. Error messages and stacks can still contain tenant or provider values, for example a provider's error text, and URLs can contain organization and record UUIDs. Restrict the Sentry project to the people who handle production incidents.

Process logs on stderr carry the same details as `error` with `type`, `message`, `code`, `stack` and `cause`. The API logs `Request failed` with trace ID, method and route; workers log the operation message. Logs contain no URLs, headers or bodies.

Temporal history receives only sanitized activity failures. The worker additionally logs `Workflow activity failed before sanitization` with the original error, stack and cause, and the workflow ID, run ID, activity ID, activity type and attempt; use those fields to match an `Activity failed` warning. With `SENTRY_DSN` set, the regular and pilot workers also capture the original exception with a `temporal` context, independent of trace sampling, and flush pending events on shutdown. Activity arguments, custom error properties and ambient user or request data are never attached. These logs and events can contain provider details and need restricted access.

## Local diagnostics

`mise exec -- pnpm dev:observe` starts PostgreSQL, Temporal, a bundled Grafana stack (Tempo, Loki, Prometheus, Pyroscope), the API, the worker and the web app. The terminal prints the Grafana address; sign in with `admin` / `admin` and open **Dashboards → Luma → Luma local performance**. Each checkout gets its own Docker project, loopback ports and telemetry volume.

No vendor account is needed. Local mode overrides hosted telemetry credentials from `.env`, traces 100% of requests and disables the stack's usage reporting. Business integrations are unchanged: the app can still call configured commerce and model providers. Run Node through `mise`, because the native Pyroscope profiler ships ABI-specific binaries. Plain `pnpm dev` does not export local telemetry.

`mise exec -- pnpm observe:verify` checks a running stack end to end: database child spans and pool waits in Tempo, metrics in Prometheus, correlated logs in Loki, API and worker profiles in Pyroscope, and that a private query and header canary never reaches an exported trace.

## Pilot and simulator

`pnpm pilot` and `pnpm pilot:worker` start the same stack and export local telemetry; `pnpm simulator` also runs the simulator service. Stop `dev:observe` before switching modes, because they share the API and web ports. `pnpm simulator:service` runs the simulator alone, without Luma or diagnostics.

Select `luma-pilot-api`, `luma-pilot-worker` or `luma-simulator` in the dashboard; plain development uses `luma-api` and `luma-worker`. Simulator provider calls continue the caller's trace into the simulator's own PostgreSQL queries, including clock ticks and webhook delivery. The pilot API prints failed requests and background sync or detection failures to its console as JSON with message, stack and causes; they also appear in Loki and on the trace.

Verify a running mode with `mise exec -- pnpm observe:verify pilot` or `... observe:verify simulator`. Verification does not reset scenarios, change seeds or resume paused runs.

## Finding a bottleneck

| Question                                        | Where to look                                                                     |
| ----------------------------------------------- | --------------------------------------------------------------------------------- |
| Which operations are slow?                      | Dashboard percentiles, throughput, failures and database time                     |
| Which query or call slowed one request?         | Explore → Tempo with the response's `x-trace-id`                                  |
| Is the connection pool saturated?               | `db.pool.acquire` spans and pool pending-request metrics                          |
| Which functions consume CPU or allocate memory? | Pyroscope `wall:cpu` and memory profiles for the service                          |
| Is JavaScript blocking the event loop?          | Event-loop delay and CPU charts                                                   |
| Is an activity waiting or retrying?             | Activity queue-delay and retry charts, then the Temporal trace                    |
| Why did a request, activity or sync pass fail?  | Loki error logs with `exception.message` and `exception.stacktrace`, or the trace |

Generate traffic before judging the dashboard: percentile and rate charts need several exports, and activity charts stay empty until an activity runs. Profiles upload about every ten seconds, and heap profiles are sampled allocations, not snapshots. Profiles are process-level evidence, not per-span CPU attribution. Span durations include waiting, so never sum nested or concurrent spans into a request duration.

## Database investigation

All `pg` queries are traced, including identity and ORM queries and transaction setup. `db.pool.acquire` covers pool waiting and, when needed, connection establishment (`db.connect`); `db.transaction` wraps a tenant-scoped transaction. Query spans carry operation, row count and a deterministic `luma.db.query_id`, never SQL text or parameters.

- `mise exec -- pnpm observe:queries <query-id>` hashes TypeScript string literals with the tracing algorithm and prints matching source locations. Dynamically assembled and ORM-generated SQL may have no match.
- `mise exec -- pnpm observe:queries` prints the top `pg_stat_statements` patterns for the API and worker roles to the terminal, never to telemetry. Statistics accumulate across runs.

Client spans include network and driver overhead; PostgreSQL statistics describe server execution. Use `EXPLAIN (ANALYZE, BUFFERS)` for plans, remembering that `ANALYZE` executes the statement: use disposable data or a rolled-back transaction for writes.

## Instrumenting an operation

Wrap an algorithm with `measureSync` or `measure` from `@luma/platform` and add its fixed name to `PerformanceOperation`. Without the local adapter the work runs directly. CPU profiles already capture functions, so add a measured boundary only where an operation-level duration helps. Temporal's tracing plugin covers workflow, client and activity boundaries.

## Local data policy and lifecycle

- Trace exports contain operation metadata, correlation IDs, query fingerprints, timing and errors. Exception events keep their message and stack, and failed requests carry their redacted URL as `luma.http.url`. Raw SQL, parameters, headers, arguments and workflow IDs are removed. Metrics use bounded dimensions and hashed pool IDs. Profiles contain function names and source paths.
- `LUMA_LOCAL_OTLP_ENDPOINT` and `LUMA_LOCAL_PROFILES_ENDPOINT` must be loopback HTTP origins; omit the profiles endpoint to run without the native profiler. Local mode is rejected for staging and production.
- To measure instrumentation overhead, run the compiled API or worker with `--env-file=.luma/env` and compare runs with both endpoints set to empty values and hosted credentials unset.
- Ctrl+C stops the app processes and leaves the Docker services running. `pnpm dev:down` stops them and keeps volumes. Telemetry lives in the worktree's `observability` volume, independent of PostgreSQL; remove only that volume to clear history.
- The Grafana image is pinned by digest. Rerun `observe:verify` after changing it. The stack is for development and testing only.
